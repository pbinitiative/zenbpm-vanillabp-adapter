## Major

### M1. Decision 3 promises a test that does not exist, and four copies of the pin can drift from the POM

- `DECISIONS.md:34`: "The pinned copies name the engine commit they came from, and a test diffs
  them against the image the integration tests run."
- `README.md:55`: "Both are written once, as `zenbpm.commit` and `zenbpm.image` in the root `pom.xml`."
- `pom.xml:106-108`: "Both move together, in one commit with the copies of api.yaml and
  zenbpm.proto in core, whose headers name the same two values."

The pin is actually written in **five** places: the root POM, the README table (`README.md` "Pinned"
table), the `api.yaml` header, the `zenbpm.proto` header, and the plan. Only the POM feeds the build.
The README's checklist for moving the pin (`README.md:59`, "changes all four") names commit, image
and the two files, but not the README table itself. Nothing fails when a later pin move forgets a
header or the table. Then the README tells users "tested against X" while the tests run Y, which
is exactly the drift decision 15 is meant to prevent.

The decision text is also stricter than what can be built. `docs/architecture/01-architecture.md:39`
says "a test diffs the shipped copies against the pinned image's `/v1/openapi` *where the engine
serves it*, otherwise the copy is the contract". At `bdd795a3` the engine does not serve its spec:
`GetSpec()` exists only inside `internal/rest/public/zz_generated.go`, and no route exposes it. So,
as decision 3 is written, it is untrue for this repository today.

The "docs are behaviour" rule (`AGENTS.md`, plan conventions) and review check 5 both make this a
finding, even though the code itself is right.

**Fix (small):**

1. Add one unit test that fails on drift. It can live in `core` or in the coverage-gate module.
   Hand `zenbpm.commit` and `zenbpm.image` in through surefire `systemPropertyVariables`, or through
   a filtered test resource. Then assert that line 1 of `core/src/main/zenbpm/api.yaml`, lines 1-2
   of `core/src/main/proto/zenbpm.proto` and the README's "Pinned" table each contain both values.
   Mutation-test it by changing one character of a header.
2. Ask the maintainers about decision 3. A decision may only change after asking, and is then
   superseded, never edited. The likely answer is a new decision that says: "the copies name the
   commit and image of the pin, and a test holds them to the POM; the engine does not serve its
   spec, so the copy is the contract". Until they answer, the test from step 1 is the closest this
   repository can get to the current wording.
3. Make `README.md:55` and the `pom.xml` comment honest: the POM is the *source* the build reads,
   and the README table and the headers are copies that the new test checks.

## Minor

### m1. The plan miscounts the generated classes

`docs/plan/epic-01-foundation.md:489`: "the jar, which carries the 59 generated classes only". The
jar has 59 classes, but only **58** are generated. The 59th is `ZenBpmAdapter.class`. Write: "the
jar carries the 58 generated classes and `ZenBpmAdapter`, no `.proto`".

### m2. The `CLUSTER_RAFT_BOOTSTRAP_EXPECT` comment reads as if the engine needed it

`EngineUnderTest.java:60`: "one node which elects itself leader instead of waiting for others to
join". At `bdd795a3` the default is already 1 (`config.go:417`, `env-default:"1"`). The TTL line
below says openly that it repeats the engine's default and why. This line should do the same, for
example: "one node which elects itself leader. 1 is the engine's default today, written here so
that a new default does not make a test wait for nodes that never come".

### m3. `ZenBpmGrpcStubsTest` claims more than it proves

`ZenBpmGrpcStubsTest.java:24-26`: "a protoc newer than that runtime fails here, and not in an
application". The test proves the match on *this build's* classpath. An application whose BOM
resolves an older `protobuf-java` will still fail at class initialisation, for example a Quarkus
release older than 3.40. Write: "…fails here, in this repository's build, instead of in the first
application built against this version". See also S1 for the application side.

### m4. The image assertion compares a value with itself

`EngineUnderTestIT.java:58` compares the container's image with `EngineUnderTest.image()`, which
reads the same filtered properties file. If the file were filtered from the wrong property, this
assertion would still pass. Two things save it in practice: the commit assertion, which asks the
running engine, and the `@sha256:` check. To make it independent, compare with a value handed in
through failsafe `systemPropertyVariables` (`zenbpm.image`) instead of with the class under test.
This is cheap but optional.

### m5. The commit assertion accepts any prefix

`EngineUnderTestIT.java:79-82` only guards against an empty string. If the engine reported `"b"`,
or any short ambiguous id, the test would pass. Also assert a minimum length (at least 7; the engine
reports 12 today), so that a changed `/system/status` format fails loudly.

### m6. The JaCoCo exclusion covers a whole package, not just generated code

`pom.xml:377` excludes `org/pbinitiative/zenbpmadapter/client/grpc/**`. Today only generated code
lives there, and S2.3.1 puts `ZenBpmJobStream` into `…client`, not `…client.grpc`. But a
hand-written class placed in `client.grpc` later, such as a helper next to the stubs, would be
silently invisible to the 85 % gate. At least extend the comment ("this package holds generated code
only; hand-written classes go to `client`"). Better, add a check to the gate that every class in that
package comes from `target/generated-sources/protobuf`.

### m7. A citation says more than the decision does

`engine-test-support/src/main/resources/zenbpm-engine.properties:2-3`: "the pin lives in one place,
'zenbpm.commit' and 'zenbpm.image' of the root POM, see decision 15". Decision 15 says the pin is a
commit plus a digest, and that supported means tested. It says nothing about "one place", and after
M1 that would not be strictly true anyway. Either cite decision 15 only for "the pin is a commit and
an image digest", or drop the citation and keep the instruction ("do not write a commit or a digest
in here; Maven fills them in from the root POM").

## Language (check 8 of `vanillabp-code-review`)

This repository's `AGENTS.md` has no "How we write" section. These findings apply the skill's
rules directly.

- **L1** `engine-test-support/src/test/resources/logback-test.xml:7-9`: "A record which its level
  drops reaches no appender". The relative clause is inverted, and most readers need two passes.
  Write: "Logback discards a record below its logger's level before any appender sees it, so
  SuppressOutputExtension could not replay it for a failing class either."
- **L2** `logback-test.xml:10-13`: "What INFO costs in a green build is the handful of lines written
  before the first extension callback (Docker detection runs in the ExecutionCondition of …), which
  no extension reaches." The subject is far from the verb, and a parenthesis sits inside it. Split:
  "In a green build, INFO still shows a handful of lines. Testcontainers writes them while it
  detects Docker, before any extension callback runs, so no extension can hold them back."
- **L3** `README.md:57-59`: "…is the copy `core/src/main/zenbpm/api.yaml`, the job stream's the copy
  `core/src/main/proto/zenbpm.proto`, both taken…". The ellipsis in "the job stream's the copy" does
  not parse on the first pass. Write two sentences: "The REST contract is the copy
  `core/src/main/zenbpm/api.yaml`. The job stream's contract is the copy
  `core/src/main/proto/zenbpm.proto`. Both come from that commit and name it in their first line."
- **L4** `NOTICE:21-24`: one sentence of four lines, with the list of files after the licence
  clause, and "from which" seems to refer to both files when it means the proto only. Split: "Two
  files are copies of interface descriptions of the ZenBPM engine (pbinitiative/zenbpm, dual-licensed
  under AGPL-3.0-or-later and an enterprise licence): core/src/main/zenbpm/api.yaml and
  core/src/main/proto/zenbpm.proto. The build generates the gRPC classes of the core jar, and the
  Java sources in its sources jar, from the proto."
- **L5** `core/pom.xml:90`: "taken from Maven Central for the machine building". The phrase "for the
  machine building" is hard to read. Write: "the build downloads protoc and its gRPC plugin from
  Maven Central, in the variant for the machine it runs on, so no machine needs them installed".
- **L6** `README.md:59-63`: the "Moving the pin…" sentence runs to five lines, and its list is
  incomplete (M1). Make it a numbered list of steps that includes "update the table above".

Checks with nothing to report: **1** (names read as sentences: `theEngineReportsThePinnedCommit`,
`EngineUnderTest`, `restAddress()`), **2** (no type names in variables; `value` in `property()` is
inherited from Camunda 8), **3** (no story, issue or person cited in code, POMs or workflows; the
plan and `open-questions.md` cite stories, which is their purpose), **4** (decisions 3, 15 and 17
all resolve in this repository's `DECISIONS.md`; m7 is about precision, not resolution), **6** (no
new decision numbers), **9** (no method too long to read).

## Licence flag (no new finding; the maintainers decide)

The branch flags the AGPL question as agreed, in NOTICE and in open question 13. Two facts for the
maintainers' answer:

- The **sources jar** of the core also ships the generated `Zenbpm.java` (≈378 KB) and
  `ZenBpmGrpc.java`, with the proto's comments copied verbatim. NOTICE mentions only "the gRPC
  classes of the core jar". L4 covers the wording.
- The engine already has a way to settle this: `LICENSING.md` at `bdd795a3` lists per-file
  exceptions under other licences (the rqlite files under MIT). Adding `openapi/api.yaml` and
  `pkg/zenclient/proto/zenbpm.proto` there, under MIT or Apache-2.0, would answer the question for
  the copies and for everything generated from them, without a separate legal document.

## Suggestions (not for this PR)

- **S1. Check the protobuf runtime at startup.** The published core requires `protobuf-java` ≥
  4.35.0 at runtime. An application whose BOM resolves an older one fails with protobuf's own error
  at the first stream class it touches. Following `vanillabp-config-validation`, a startup check
  (comparing `com.google.protobuf.RuntimeVersion` with the gencode version) could name the property
  or BOM to change. This belongs in the story that first opens the stream (S2.3.1) or into `GAPS.md`.
- **S2. Ship the logback template instead of copying it.** Copies per module drift. That drift is
  exactly why Camunda 8 created its `test-support` module. `engine-test-support` could ship a
  `zenbpm-engine-logback.xml` fragment, and each module's `logback-test.xml` would only
  `<include resource="…"/>` it.
- **S3. A shared engine per module.** Each IT class now starts its own engine (≈6 s). E2–E4 add many
  IT classes. Camunda 8's `ClusterUnderTest.sharedCluster()` (started once, reaped by Ryuk) is the
  proven pattern, if build time becomes a concern.
- **S4. `source:jar` forks `generate-sources`.** That runs `protobuf:generate` a second time in every
  core build (log: ">>> source:3.4.0:jar (attach-sources) > generate-sources"). It is cheap because
  of the plugin's incremental cache, and it was already like this before the branch. `jar-no-fork`
  avoids the fork. Related noise, also pre-existing: Maven warns "the encoding used to copy filtered
  properties files have not been set", which `<propertiesEncoding>` silences.

## Nits

- `EngineUnderTestIT.java:35,37`: `private static final` fields named `engine` and `http`. Camunda 8
  ITs write `CAMUNDA`. Either style is fine; just pick one for the repository.
- The plan's "3 tests in about 5 s" took 6.1 s here. This is not worth changing; it only shows the
