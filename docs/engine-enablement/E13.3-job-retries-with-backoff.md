# ZenBPM feature: job retries with backoff

Story for the `zenbpm` engine (`github.com/pbinitiative/zenbpm`), analysed against commit `33a0906f`
(2026-09-19). It closes GAPS 6 of the adapter plan and answers open question 3 ("medium priority;
retry strategy?"). Paths are relative to the `zenbpm/` repository unless prefixed.

## 1. Why

A worker which cannot finish a job because of a transient failure - a downstream service is down,
a database deadlock, a network blip - has two choices today, and both are wrong:

- report the failure with `fail`: the engine marks the job `failed`, creates an incident and turns
  the process instance `failed` at once. An operator has to resolve the incident by hand although
  the next attempt would very probably have succeeded;
- report nothing: the job sits behind its lock (configurable per subscription since E13.1) and is
  handed out again when it lapses; since E13.1 a worker CAN say "not now, try again in a minute" by
  extending the lock by a minute, which is what the adapter plan does meanwhile - but the engine
  counts nothing, a new node or a leader change starts over, and after a persistent failure nothing
  ever produces an incident, so the workflow stands still without anybody noticing.

`zenbpm:taskDefinition retries="3"` is parsed (`pkg/bpmn/model/extensions/task_definition.go`) and
ignored; the REST `Job` schema already declares a `retries` property "Remaining retries"
(`openapi/api.yaml`) which is never populated (`internal/rest/server.go` `mapProtoJob`). Models drawn
with the Camunda Modeler carry the attribute and expect Zeebe's semantics.

The adapter plan works around the gap with a local backoff per job key and its own attempt counter
(`docs/architecture/02-design-decisions.md`, decision 8; `docs/plan/epic-06-task-processing.md`
S6.2.1), which is state the engine should own: two nodes of one application cannot share it, and a
restart forgets it.

Two older ZenBPM tasks asked for the same thing from the operator's side: "job incidents and retry
strategies" (configurable strategies, visibility into job health and historic failures, operator
APIs to inspect, resolve or reset) and "job-level retry mechanism" (automatic retries with a
configurable policy, persisted retry metadata, no duplicate side effects between attempts). Both
were written more than a year ago against an engine which has since gained incidents, incident
resolution and the job manager. Section 11 holds every requirement of the two with what became of
it; what is still missing is folded into sections 4.8 to 4.11.

## 3. Goal and non-goals

**Goal.** A job carries a number of remaining retries, initialised from its task definition. A
worker which fails a job without an error code says how many retries remain (or lets the engine
decrement) and how long to wait; while retries remain the job becomes deliverable again after the
backoff and NO incident is created; at zero an incident is created as today. Resolving that incident
gives the job its retries back. Everything is visible on the job through REST and the stream.

**Non-goals**: retries for internal (engine-handled) tasks and for engine-internal work such as
firing a timer or correlating a message (section 11 says why and where that belongs); headers as
worker parameters (the other half of the TODO, a separate story); a persisted history which outlives
the process instance (attempt history is deleted with the instance's jobs, like everything else).

## 4. Design

### 4.1 Semantics (the retry strategy, answering open question 3)

Zeebe's model, because the Camunda Modeler writes it and the adapter authors know it:

1. **Initial retries** come from `zenbpm:taskDefinition retries`. A literal integer (`"3"`), or a
   FEEL expression starting with `=` evaluated at job creation against the job's input scope
   (`engine.evaluateExpression`). Absent or empty -> the engine default `jobs.defaultRetries`.
2. **Default when the attribute is absent: `1`** (decision 9.1 below). One attempt, then an
   incident - which is exactly today's behaviour, so no existing model or client changes behaviour
   by upgrading. Zeebe's default is 3; an operator who wants parity sets `JOBS_DEFAULT_RETRIES=3`.
3. **A fail request carries** `retries` (optional; the remaining count the worker decides on) and
   `retryBackoff` (optional; how long the job must wait before it is deliverable again). A missing
   `retries` means "one less than now" (`job.retries - 1`); a missing backoff means the definition's
   policy for this attempt, and where the definition has none the engine default, which is "at
   once" (4.8).
4. **Remaining > 0**: the job stays `active`, `retries` is set to the remaining value,
   `retryAt = now + backoff` (or `NULL`), the failure message is recorded on the job, no incident,
   the instance stays `active`. The distribution loop and `GET /v1/jobs?state=active` still see the
   job (it IS active), but the leader does not hand it out before `retryAt`.
5. **Remaining = 0**: `failJobWithIncident` as today; the incident message is
   `"<message> (retries exhausted)"` so an operator sees the difference to an error-code failure.
6. **A fail with an error code** is a BPMN error, never a retry: retries are not consulted or
   decremented, exactly as today.
7. **Resolving the incident** of an exhausted job resets `retries` to the initial value re-evaluated
   from the task definition (the same place `ResolveIncident` already re-evaluates the input
   mappings) and clears `retryAt`; the job is active again as today.
8. **Terminating** the token (interrupting boundary event, instance cancellation) during a backoff
   terminates the job as today (`terminateActiveJobsForToken` selects `Active`).
9. **Negative retries** in a request are a `400`; `retries` larger than the current value is allowed
   (a worker may top up), capped at `jobs.maxRetries`.

### 4.2 Storage (`internal/sql/migrations/0016_job_retries.up.sql` and `.down.sql`)

```sql
-- Remaining attempts before a failure without an error code becomes an incident. Initialised
-- from zenbpm:taskDefinition retries (default: the engine's jobs.defaultRetries). Existing rows
-- get 1, which is the behaviour they had: one failure, one incident.
ALTER TABLE job ADD COLUMN retries INTEGER NOT NULL DEFAULT 1;
-- Failures without an error code so far; attempts + retries = what the series started with.
ALTER TABLE job ADD COLUMN attempts INTEGER NOT NULL DEFAULT 0;
-- Unix millis before which a failed-but-retryable job must not be handed out again. NULL = now.
ALTER TABLE job ADD COLUMN retry_at INTEGER;
-- The message of the last failure without an error code, for operators reading the job.
ALTER TABLE job ADD COLUMN last_failure_message TEXT;
-- The backoff policy of the definition at job creation, normalised ("PT10S,PT1M"); NULL = none.
ALTER TABLE job ADD COLUMN retry_backoff TEXT;

-- One row per failure without an error code (section 4.9); deleted with the instance's jobs.
CREATE TABLE IF NOT EXISTS job_failure(
    key INTEGER PRIMARY KEY,           -- snowflake id
    job_key INTEGER NOT NULL,
    process_instance_key INTEGER NOT NULL,
    attempt INTEGER NOT NULL,          -- 1-based
    failed_at INTEGER NOT NULL,        -- unix millis
    retry_at INTEGER,                  -- NULL where the failure created the incident
    message TEXT NOT NULL,
    incident_key INTEGER               -- set on the failure which exhausted the retries
);
CREATE INDEX IF NOT EXISTS idx_job_failure_job_key ON job_failure(job_key);
CREATE INDEX IF NOT EXISTS idx_fk_job_failure_process_instance_key ON job_failure(process_instance_key);

-- The job an incident was created for (section 4.10); NULL for incidents without a job.
ALTER TABLE incident ADD COLUMN job_key INTEGER;
```

Down: `DROP TABLE job_failure` and `ALTER TABLE ... DROP COLUMN` for the added columns (the pattern
of `0013_*.down.sql`). `make generate` regenerates `internal/sql`. Queries:

- `SaveJob`: the new columns in the insert and the `ON CONFLICT DO UPDATE SET` list;
  `SaveJobFailure`, `FindJobFailures` (paged, newest first), `DeleteProcessInstancesJobFailures`;
  `SaveIncident` gains `job_key`.
- `GetWaitingJobs` and `FindActiveJobsByType`: `AND (retry_at IS NULL OR retry_at <= @now)`; the
  partial index stays useful (`state = 1` leads), `retry_at` is evaluated on the few active rows.
- `runtime.Job` gains `Retries int32`, `Attempts int32`, `RetryAt *time.Time`, `LastFailureMessage
  *string`, `RetryBackoff []time.Duration`; `runtime.Incident` gains `JobKey *int64`; a new
  `runtime.JobFailure`; `partition_persistence.go` maps them in `SaveJobWith` and the read side.

### 4.3 Engine (`pkg/bpmn`)

- `createInternalTask` (`jobs.go`): `job.Retries = engine.initialRetries(element, jobVarHolder)`;
  the helper reads `TaskDefinition.Retries` from every job-producing element (`GetTaskDefinition()`
  on `InternalTask` - service, send, user, external business-rule task, message throw/end events),
  evaluates a leading `=`, applies the default, and returns an error for a non-integer or negative
  result, which ends in an incident at job creation like any other evaluation failure.
- Deploy-time validation (`pkg/bpmn/model/bpmn20/helper.go` `ResolveReferences`): a literal
  `retries` which is not a non-negative integer is rejected with `400` naming the element, like an
  unsupported element is today; an expression is accepted (checked at runtime).
- `JobFailByKey(ctx, key, message, errorCode, variables, retries *int32, retryBackoff *time.Duration)`:
  after `refreshAndValidateJob`, if `errorCode != nil` -> the existing branch. Else
  `remaining := job.Retries - 1; if retries != nil { remaining = *retries }`; `remaining < 0` ->
  `BadRequest`; `remaining > 0` -> `retryJob(...)`: set `Retries`, `RetryAt`, `LastFailureMessage`,
  keep `State = Active`, `SaveJob`, `Flush`, metric `JobsRetried`, span attribute; return. Else the
  existing `failJobWithIncident` with the suffixed message.
- `ResolveIncident` (`incident_api.go`): where the incident's job is found, after
  `reevaluateJobInputVariables`, `job.Retries = engine.initialRetries(...)`, `job.RetryAt = nil`.
- `ActivateJobs` (the library API) honours `retry_at` through the changed query.

### 4.4 Wire contracts

Public gRPC (`pkg/zenclient/proto/zenbpm.proto`):

```proto
message JobFailRequest {
  int64 key = 1;
  string message = 2;
  string error_code = 3;
  bytes variables = 4;
  optional int32 retries = 5;         // remaining retries; absent = current - 1
  int64 retry_backoff_ms = 6;         // 0 = deliverable at once
}
message WaitingJob {
  // ... 1-7 (and lock_until = 8 from E13.1) ...
  int32 retries = 9;                  // remaining retries at delivery
}
```

Internal gRPC (`internal/cluster/proto/zen_cluster.proto`): `FailJobRequest` gains
`optional int32 retries = 6; int64 retry_backoff_ms = 7;`; `Job` gains `int32 retries = 12;
int64 retry_at = 13; string last_failure_message = 14;`; `InternalJob` gains `int32 retries`.

REST (`openapi/api.yaml`):

- `POST /v1/jobs/{jobKey}/fail` body gains `message` (string), `retries` (integer, minimum 0),
  `retryBackoff` (ISO-8601 duration string, `"PT10S"`, the format the BPMN timers use).
  `400` for a negative `retries` or an unparsable duration.
- `Job` schema: `retries` (already declared) is populated; new `retryAt` (date-time, nullable),
  `lastFailureMessage` (string, nullable). `mapProtoJob` fills them.
- `GET /v1/jobs` keeps answering a job in backoff as `active` (it is); the `retryAt` field says why
  nobody has it.

### 4.5 Configuration (`internal/config`, `docs/reference/configuration.md`)

Section `jobs`: `defaultRetries` (`JOBS_DEFAULT_RETRIES`, default `1`, minimum 1) and `maxRetries`
(`JOBS_MAX_RETRIES`, default `100`). Validated at startup.

### 4.6 Go client (`pkg/zenclient/grpc.go`)

`WorkerError` gains `Retries *int32` and `RetryBackoff time.Duration`; `failWorkerJob` copies them
into `JobFailRequest`. A handler which wants the default decrement returns `&WorkerError{Err: err}`
as today. `failPanickedJob` keeps sending no retries (a panic decrements like any failure).

### 4.7 Distribution (`internal/cluster/jobmanager`)

No change in the leader's loop: `GetWaitingJobs` filters `retry_at`, and the loop already polls
every 100 ms to 1 s, so a job becomes deliverable within one poll interval after its backoff. The
`failJob` of the server still removes the lock entry after the engine call, which is right for both
outcomes.

### 4.8 Engine-side default retry policy on the task definition

A worker which sends no `retryBackoff` gets "at once" today (4.1 rule 3). The older tasks asked for a
policy the MODEL or the engine owns, so a job is not hammered by a worker which knows nothing about
backoff. Camunda 7's `failedJobRetryTimeCycle` is the precedent worth copying, not Zeebe's absence
of one:

```xml
<zenbpm:taskDefinition type="charge-card" retries="4" retryBackoff="PT10S,PT1M,PT10M"/>
```

- `retryBackoff` is an ISO-8601 duration or a comma-separated list of them. Attempt `n` (the n-th
  failure of the job, counted from 1) waits the n-th entry; past the end the last entry repeats.
  `"PT10S"` is a fixed delay, `"PT10S,PT20S,PT40S,PT80S"` an exponential one, `"PT0S"` none.
  A leading `=` makes it a FEEL expression evaluated at job creation (result: string or list of
  strings).
- Engine default `jobs.defaultRetryBackoff` (`JOBS_DEFAULT_RETRY_BACKOFF`, default `PT0S`, so an
  upgrade changes nothing), applied where the attribute is absent.
- Precedence, most specific wins: the `retryBackoff` of the fail request beats the definition's
  policy beats the engine default. The adapter sends one per request, so the policy is what its
  users' plain workers get.
- Persisted with the job at creation as a normalised string (`retry_backoff TEXT`), so a redeployed
  model does not change the policy of a running job; `jobs.maxRetryBackoff` (`PT24H`) caps every
  entry. A literal which does not parse is refused at deployment like a bad `retries`.

### 4.9 Attempt history and observability

What an operator asked for in the older tasks and E13.3 did not yet give: how often a job failed,
when, why, and when it comes back.

- `job.attempts INTEGER NOT NULL DEFAULT 0`: the number of failures without an error code so far.
  Incremented in `retryJob` and in `failJobWithIncident`; reset to 0 when an incident is resolved
  (the operator starts a fresh series) - so `attempts + retries` always equals the initial value the
  series started with.
- Table `job_failure(key INTEGER PRIMARY KEY, job_key INTEGER NOT NULL, process_instance_key
  INTEGER NOT NULL, attempt INTEGER NOT NULL, failed_at INTEGER NOT NULL, retry_at INTEGER,
  message TEXT NOT NULL, incident_key INTEGER)`, index on `job_key`; one row per failure without an
  error code, `incident_key` set on the row which exhausted the retries. Deleted with the instance's
  jobs (`DeleteProcessInstancesJobs` gets a sibling; the history TTL cleanup calls it). `last_failure_message`
  on the job stays as the cheap read; the table is the history.
- REST `GET /v1/jobs/{jobKey}/failures` -> `JobFailurePage` (paged, newest first, up to 1000) and the
  fields `attempts` and `retryBackoff` on `Job`. The process instance's element history
  (`GET .../history`) is untouched: it records the element, not the attempts.
- `WaitingJob.attempt` (int32; 1 for the first delivery of a fresh series, `attempts + 1` after
  failures) travels with every delivery, so a worker can make its side effects idempotent per
  (job key, attempt) or tell a redelivery of the same attempt from a retry.
- One WARN per retryable failure: `job <key> of type <type> in instance <key> failed (attempt
  <n>/<n + remaining>): <message>; next delivery not before <retryAt>`; one ERROR when the incident
  is created, naming the attempts. Metrics: `jobs_retried{type}` (4 above) and a histogram
  `job_retry_backoff_ms{type}` of the backoffs applied.

### 4.10 The incident names its job and the series which led to it

`runtime.Incident` and the `incident` table gain `job_key INTEGER` (nullable; NULL for incidents
without a job), REST `Incident.jobKey`, and the incident message of an exhausted job reads
`"<last message> (job <key>: <attempts> attempts, retries exhausted)"`. With the job key an operator
walks from the incident to `GET /v1/jobs/{jobKey}` and `.../failures` without searching the
instance's jobs by element id, which is what the older task's "incidents contain job ... error, retry
info" asks for. The incident row still points at the token and the element instance, so nothing
which reads incidents today changes.

### 4.11 Operator API: update retries

`POST /v1/jobs/{jobKey}/retries` body `{ "retries": <int, minimum 1>, "retryAt": <date-time,
optional> }` -> `204`. Sets the remaining retries of an `active` or `failed` job; an absent `retryAt`
clears the backoff so the job is deliverable at once. On a `failed` job with an unresolved incident
the incident stays open: the operator resolves it as today, and the resolution then keeps the
retries just set instead of re-evaluating the definition (rule 7 of 4.1 becomes "restores the
definition's retries unless an update set them"). Zeebe's `UpdateJobRetries` is the precedent. `404`
for an unknown job, `400` for a count below 1 or above `jobs.maxRetries`, `409` for a job which is
`completed` or `terminated`. Internal RPC `UpdateJobRetries` shaped like `AssignJobToAssignee`.

## 5. Behaviour to specify precisely

1. A model with `retries="3"`: the first two failures without an error code leave the job `active`
   with `retries` 2 then 1 and no incident; the third creates the incident, the job is `failed`, the
   instance `failed`.
2. A model without the attribute and an engine with the default `1`: the first failure without an
   error code creates the incident - identical to today; the e2e tests `service_task_job_fail_*` and
   `user_task_job_fail_*` stay green unchanged.
3. A fail with `retryBackoff = PT2S`: the job is not handed out (stream) and not returned by the
   library's `ActivateJobs` for 2 s, and is afterwards; `retryAt` on the REST job says when.
4. A fail with an explicit `retries = 5` on a job with 1 left sets 5 (capped by `maxRetries`).
5. A fail with an error code never changes `retries` and never records a `lastFailureMessage`.
6. Resolving the incident of an exhausted job restores the definition's retries (re-evaluated) and
   clears `retryAt`.
7. `retries` on `WaitingJob` equals the value the REST job shows at the same moment.
8. An old client sending the previous `JobFailRequest` (no field 5) decrements by one; on an
   unmodelled task that is the incident it always got.
9. The failure message of a retryable fail is readable on the job (`lastFailureMessage`) and is
   part of the incident message once retries are exhausted.
10. A definition with `retryBackoff="PT1S,PT3S"` and `retries="4"`: the failures wait 1 s, 3 s, 3 s;
    a fail request naming its own `retryBackoff` overrides the entry for that attempt only.
11. `job.attempts` counts failures without an error code; `GET /v1/jobs/{key}/failures` lists one
    row per such failure with attempt number, time, message and next delivery; the row which
    created the incident carries the incident key.
12. Every delivery carries `attempt`; two deliveries of one attempt (a lapsed lock, E13.1) carry the
    same number, a delivery after a fail carries the next.
13. The incident of an exhausted job carries `jobKey`; resolving it resets `attempts` to 0 and, unless
    an update set them, the retries to the definition's value.
14. `POST /v1/jobs/{key}/retries` on a job in backoff makes it deliverable at once when `retryAt` is
    omitted; on a `completed` or `terminated` job it answers `409`.

## 6. Implementation steps

Follow `AGENTS.md`: `make generate` after SQL, OpenAPI or proto changes; tests with testify and
`require.Eventually`; a change without a test which fails before it is not finished; review with
the `zenbpm-code-review` skill.

## 8. Acceptance criteria

- [ ] `zenbpm:taskDefinition retries` (literal or FEEL) initialises `job.retries`; absent -> the
  configured default, which is `1` and therefore today's behaviour.
- [ ] A fail without an error code and with retries remaining leaves the job `active`, decrements
  (or sets) `retries`, records `retryAt` and `lastFailureMessage`, creates no incident and leaves
  the instance `active`.
- [ ] A job in backoff is neither handed out over the stream nor returned by `ActivateJobs` before
  `retryAt`, and is afterwards without any operator action.
- [ ] A fail with no retries left creates the incident and fails job and instance as today, with the
  failure message and "retries exhausted" in the incident.
- [ ] A fail with an error code behaves exactly as today.
- [ ] Resolving the incident restores the definition's retries and clears the backoff.
- [ ] The fields exist on both protos and REST (`message`, `retries`, `retryBackoff` in the request;
  `retries`, `retryAt`, `lastFailureMessage` on the job; `retries` on `WaitingJob`), with `400` for
  a negative count or a bad duration; clients built against the previous contract work unchanged.
- [ ] `jobs.defaultRetries`, `jobs.maxRetries`, `jobs.defaultRetryBackoff` and `jobs.maxRetryBackoff`
  are configurable and documented.
- [ ] `zenbpm:taskDefinition retryBackoff` (duration, list or FEEL) is applied per attempt where a
  fail request names no backoff; the request's value wins for its attempt; the engine default is
  `PT0S`.
- [ ] Every failure without an error code increments `attempts`, writes a `job_failure` row (attempt,
  time, message, next delivery, incident key where one was created) readable through
  `GET /v1/jobs/{jobKey}/failures`, and logs one WARN naming job, type, instance, attempt and next
  delivery; the incident logs one ERROR.
- [ ] `WaitingJob` carries `attempt`; the REST job carries `attempts` and `retryBackoff`.
- [ ] The incident of an exhausted job carries `jobKey` and names the attempts in its message.
- [ ] `POST /v1/jobs/{jobKey}/retries` sets the remaining retries (and optionally the next delivery)
  of an active or failed job with `400`/`404`/`409` as specified; a later incident resolution keeps
  the updated count.
- [ ] `job_failure` rows are deleted with the instance's jobs by the history cleanup.
- [ ] `pkg/zenclient` `WorkerError` carries `Retries` and `RetryBackoff`.
- [ ] Metric `jobs_retried` exists; `jobs_failed` keeps its meaning.
- [ ] Docs of section 6.9 are updated; the migration has an up and a down; tests of section 7 exist
  and pass; `make test`, `make test-e2e`, `make go-static-analysis` green; `make generate` leaves
  no diff.

## 9. Decisions to take before or while implementing

1. **Default retries `1` (behaviour-preserving) or `3` (Zeebe parity).** The story chooses `1` so an
   upgrade changes nothing and makes parity a configuration value. Choosing `3` instead changes the
   outcome of every unmodelled failing task after the upgrade and needs a release-notes warning plus
   updates to the existing `*_job_fail_*` e2e tests.
2. **Where the failure variables of a retryable fail go.** The story stores nothing but the message
   (the variables of a `fail` are meant for the error-code path). Zeebe merges them into the job's
   local scope; if that is wanted, merge into `job.InputVariables` so the next delivery sees them.
3. **Backoff format on REST.** ISO-8601 (`PT10S`) as chosen, matching BPMN timers, versus integer
   milliseconds matching the proto. One of the two, written into the OpenAPI description.
4. **Job state during backoff.** `active` with `retryAt` (chosen: it IS waiting for a worker, and the
   REST enum stays as it is) versus a new state `retrying` (more explicit, but a new enum value in
   the REST contract and in every consumer).
5. **An "update retries" endpoint** is IN scope (4.11), promoted from a follow-up because the older
   "job incidents and retry strategies" task asked for an operator API to reset. Keep it minimal:
   count and next delivery, nothing else.
6. **Attempt history in a table or as JSON on the job.** A table (chosen: pageable, indexable,
   deleted with the jobs) versus a bounded JSON array on the job row (simpler, but grows the row
   the distribution loop reads on every round). If the table is too much for the first release,
   ship `attempts` and `lastFailureMessage` first and the table as a follow-up; the REST endpoint
   is additive.
7. **Backoff policy on the definition: list or `R`-cycle.** A comma-separated list (chosen, one
   parser, exponential expressible) versus Camunda 7's `R3/PT5M` cycle syntax, which the timer
   parser already understands but cannot express a growing delay. Decide one; do not accept both.

## 10. What the adapter does once this ships (the adapter twin of E13.3)

- A `@WorkflowTask` which throws is reported with `POST /v1/jobs/{key}/fail {message: "<exception
  type>: <message>", retryBackoff: <retry-backoff resolved per task>}` and no `retries`, so the
  engine decrements; the model's `retries` (or the engine default) decides when it becomes an
  incident. `ZenBpmLocalRetry` and `max-redeliveries` are removed; `retry-backoff` stays and moves
  to the request (`docs/plan/epic-06-task-processing.md` S6.2.1 superseded).
- The adapter sets `retries` on the tasks it rewrites where the model carries none and the
  application configured `vanillabp.adapters.<id>.retries` (adapter, module, workflow, task), so an
  application decides its attempt count without touching the BPMN.
- Decision 8 is superseded; GAPS 6 closed; Deviations 6 removed;
  `docs/analysis/02-spi-requirements-mapping.md` row "Technical failure" becomes SUPPORTED.
- The Camunda 8 wording for the incident message ("the exception's TYPE next to its message, because
  that text is what an operator reads") carries over: `lastFailureMessage` is what a ZenBPM operator
  reads.

## 11. Disposition of the requirements of the two older tasks

Both tasks predate the job manager, the incident API and the history TTL. Every requirement is listed
with what is true of the engine today (commit `33a0906f`), what E13.3 already covered before this
revision, and what this revision added or rejected.

### "Job incidents and retry strategies"

| Requirement | Today | Disposition |
|---|---|---|
| Record a job incident when execution fails | exists: `failJobWithIncident` creates one per failed job (`pkg/bpmn/jobs_api.go`) | kept, but ONLY when retries are exhausted (4.1). The literal acceptance criterion "an incident whenever a job fails" contradicts retries: a retryable failure is a `job_failure` row (4.9), not an incident. Stated so in the docs |
| Retry strategies: fixed delay, exponential backoff, max retries | none | max retries = `retries` (4.1); fixed and exponential delay = `retryBackoff` on the definition, a single duration or a list (4.8), plus the worker's per-request backoff. An engine-computed exponential formula is not added: a list expresses it without a second grammar |
| Visibility into job health and historic failures | `retries` in the REST schema, never filled; nothing historic | `retries`, `attempts`, `retryAt`, `lastFailureMessage`, `retryBackoff` on the job; `GET /v1/jobs/{key}/failures` (4.9); metrics and log lines |
| APIs to inspect incidents | exists: `GET /v1/process-instances/{key}/incidents` | unchanged; `Incident.jobKey` added (4.10) so an incident leads to its job |
| APIs to resolve incidents | exists: `POST /v1/incidents/{key}/resolve` re-activates the job | kept; resolution now also resets `attempts` and restores retries (4.1 rule 7) |
| APIs to reset | none | `POST /v1/jobs/{key}/retries` (4.11) |
| AC: incidents contain job, process instance, activity, error, retry info, timestamps | process instance, element, element instance, message, created/resolved timestamps exist; no job link, no retry info | `jobKey` column and field, attempts in the message (4.10); the retry info itself is on the job and its failures, not duplicated into the incident row |

### "Job-level retry mechanism"

| Requirement | Today | Disposition |
|---|---|---|
| Automatic retries of failed jobs before marking them failed | none: first `fail` = incident | the whole of E13.3 for EXTERNAL jobs |
| Retries for asynchronous engine work: "async before/after tasks, timers, message subscriptions" | ZenBPM has no async-before/after; a timer whose trigger fails is only logged (`ProcessTimer`) and is picked up again by the next timer-manager poll because its row stays due; a message publication which fails creates an incident (`handleMessagePublicationError`); a token which stops mid-run is recovered on the leader's startup, instances in `Failed` state excepted | REJECTED for this story: it is Camunda-7 vocabulary for engine-internal work, a different mechanism from a worker failing a job. What of it holds - a structured retry with backoff for a timer trigger or a message correlation which failed for a technical reason instead of a log line or an immediate incident - is a feature of the engine alone, written up in the engine repository as `zenbpm/docs/superpowers/specs/2026-09-19-engine-internal-transient-failures.md` |
| Configurable retry policy: attempts, delay, backoff strategy | none | `retries` + `retryBackoff` on the definition, engine defaults, request override (4.1, 4.8) |
| Log retry attempts | none | one WARN per retryable failure, one ERROR per incident (4.9) |
| Expose retry metadata: attempt count, error message, next retry timestamp, via API | none | `attempts`, `lastFailureMessage`, `retryAt` on the job; `attempt` on every delivery; the failures endpoint (4.9) |
| Persist retry metadata | none | columns on `job`, table `job_failure`, deleted with the instance |
| Avoid duplicate side effects by idempotency or rollback between attempts | a job keeps its key across attempts; nothing else | the engine cannot roll back a worker's side effects and does not pretend to. What it gives the worker: a stable job key, the `attempt` number on every delivery, unchanged input variables between attempts (decision 9.2 keeps failure variables out of the job's scope) and, with E13.1, a lock which is not lost mid-handler. The docs say in one sentence that idempotency of side effects stays the worker's - which is also VanillaBP's contract (`ADAPTER-AUTHORS.md`, section 5) |
| AC (listed twice in the original): retried up to the limit, delayed per policy, metadata persisted and visible | - | all three are acceptance criteria of section 8 |
